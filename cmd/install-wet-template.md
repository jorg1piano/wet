# wet — parallel-worktree helper

This skill has two modes. Activate the right one based on what the user is doing:

1. **Config mode** — the user is writing, editing, or debugging `.wet.yaml`. Follow the "Config guide" sections below.
2. **Team mode** — the user wants to boot the dev stack and spawn an agent team. Follow the "Team guide" sections below.

If the user says something ambiguous, ask which they want.

---

# Config guide

Use this when the user is writing a fresh `.wet.yaml`, editing an existing one, asking what a field does, debugging a hook failure, or migrating a project to `wet`.

## Quick schema orientation

A `.wet.yaml` has these top-level keys, all optional except `project_name`:

- `project_name` — required. Docker-compose-safe name for generated compose project names.
- `main_branch` — trunk new worktrees are cut from, and the default PR base. Defaults to `main`.
- `copy` — files and directories copied from the main repo into each new worktree.
- `port_stride` — default port stride (how far ports advance per slot). Defaults to `10`.
- `ports` — named port declarations. Each port gets `base + slot * stride`.
- `pools` — named lists of opaque strings round-robined across worktrees.
- `pool_grow` — optional per-pool auto-expand strategy. Currently supports `android-emulator`: when a pool is exhausted, creates a new AVD, cold boots it, and appends the new serial to `.wet.yaml`.
- `env` — Go `text/template` strings, resolved to a fixed point; the derivation layer everything else reads.
- `outputs` — the environment files wet generates, declared inline: which keys each file holds and where it is written. Generated by `wet setup` and `wet env pull`.
- `secrets` — the store, the availability policy, and one definition per credential. Optional; without it wet contacts no store.
- `hooks` — shell commands run around worktree lifecycle events (`post_create`, `pre_remove`).
- `pr` — configures `wet pr create` behavior (base branch, body template).

**`render:` and `secrets.sections:` no longer exist.** A config containing
either fails to load with a migration message. Never write them, and if you see
them in a user's config, migrate it (see "Migrating a config off `render:`").

## Read the schema of record first

`wet.example.yaml` sits next to this file, in the same
`.claude/skills/wet/` directory. It is a real local file, not a URL: open it
with Read before writing or editing any `.wet.yaml`. It is the fully annotated
schema — every key, its validation rule, and why it exists. This skill covers
how to *use* the schema; that file defines it. If the two ever disagree,
`wet.example.yaml` wins.

## Template fields reference

Every `env:` value and hook command is rendered with this data. Rendering uses
`missingkey=error`: a reference to a field that does not exist fails the
operation loudly rather than producing an empty string.

`outputs:` names the *same* values, but as bare names rather than templates —
`include: [APP_PORT]`, `values: { device: { from: Handles.devices } }`. There is
no `{{ }}` anywhere in an `outputs:` block.

| Key | Value | Example |
|---|---|---|
| `{{.ProjectName}}` | `project_name` from config | `myapp` |
| `{{.Branch}}` | Raw git branch name | `feature/foo` |
| `{{.BranchSafe}}` | Branch with slashes flattened, safe for Docker names | `feature-foo` |
| `{{.Slot}}` | Allocated slot (main = 0, worktrees from 1) | `1` |
| `{{.APP_PORT}}`, … | One key per declared port | `8090` |
| `{{.Pools.devices}}`, … | The item this worktree claimed from pool `devices` | `emulator:wet-myapp-1` |
| `{{.Handles.devices}}`, … | The address that item answers to right now | `emulator-5554` |

`Pools` vs `Handles`: the pool item is the durable name the lifecycle reasons
about; the handle is what a command must target now. For an emulator the item
is `emulator:<AVD_NAME>` and the handle is the live adb serial; for everything
else the handle equals the item. Use `{{.Handles.x}}` in commands, `{{.Pools.x}}`
when you mean the claim itself.

`env:` entries are also available to `outputs:` and hooks, so a derived value is
written once and consumed everywhere.

## How to populate a fresh `.wet.yaml`

When a user says *"write a .wet.yaml for my project"*, follow this recipe:

### Step 1. Project name
Ask: **"What's the project name?"** Must match `[a-z0-9][a-z0-9_-]*`.

### Step 2. Files and directories to copy
Ask: **"What files/dirs are not in git but needed per-worktree?"** Probe: `.env*`, `.vscode/`, `.idea/`, `.claude/settings*.json`, `config/local.*`. Check `.gitignore` for candidates.

Split the answers in **three**:

- **Identical in every worktree** (`.claude/settings.json`, most of `.vscode/`) — `copy:` them.
- **Holds a port, hostname, device id, or secret** — an `outputs:` entry, never
  a copy. A copy carries the previous worktree's ports. Editor config is the
  subtle case: `.vscode/launch.json` *looks* static, but a debugger attaches to
  this slot's port. Point it at the generated `.env`
  (`--dart-define-from-file` / `envFile`) and it becomes static for real, so
  `copy:` or commit it. See below.
- **Genuinely machine-local** (a LAN IP, a personal API key) — `.env.local`,
  which is gitignored and overrides `env:` entries.

### Step 3. Ports
Ask: **"What ports does your project listen on?"** Probe: `docker-compose.yml` ports, `Dockerfile` EXPOSE, Go `:NNNN` listen strings, `package.json` scripts. Name each port `UPPER_SNAKE_CASE`.

### Step 4. Compose project name
If Docker Compose is used, add: `env: { COMPOSE_PROJECT_NAME: "{{.ProjectName}}-{{.BranchSafe}}" }`

### Step 5. Pools (only if needed)
Ask: **"Any scarce one-per-worktree resources?"** (device IDs, DB snapshots, test fixtures). Most projects skip this.

### Step 6. Outputs — the env files each package reads
Ask: **"Which env files does each package read, and what keys are in them?"**
Probe: existing `.env*` files, `env_file:` in compose, `--dart-define-from-file`
args, any `.env.example`. One `outputs:` entry per file. See "Generated env
files (`outputs:`)" below for the schema and the rules.

If any of those keys is a credential, don't hand-write the block — run
`wet secrets setup` for the providers the project uses, which writes the
definitions and wires them into an output. See "Secrets" below.

### Step 7. Hooks
Ask: **"What should happen on worktree create/destroy?"** Common: start/stop Docker, run migrations. For adb port forwarding don't write a script — add `wet mobile reverse-tcp` as a `post_create` hook, which reverses every allocated port onto the device this worktree claimed. You do **not** need a hook to generate env files — `wet setup` generates every declared output before hooks run.

If you reach for `sed` to patch a port into a config file, check first whether that file could just be a declared `outputs:` entry — that's the same job without the in-place edit.

### Step 8. PR config
If the project uses GitHub, optionally add `pr: { base: main }`.

### Step 9. Gitignore the machine-local state files

wet writes two files at the **main repo root** that must never be committed:

- `.wet-worktrees.json` — the allocation state (slots, ports, pool claims,
  absolute worktree paths). Per-machine, not per-repo.
- `.wet-worktrees.lock` — the empty flock file guarding allocation. Pure
  scratch; it appears the first time anyone runs `wet worktree create` and
  otherwise just clutters `git status`.

`wet install wet-skill` adds both by name. List them the same way if you are
writing the `.gitignore` by hand:

```gitignore
.wet-worktrees.json
.wet-worktrees.lock
```

A `.wet-worktrees.*` glob ignores them just as well, but wet matches whole
lines when it checks, so it will not recognise the glob as covering them and
will append both names underneath it.

`wet install wet-skill` already adds `.env.worktree`, `.env.local` and
`.wet.local.yaml`, and every output wet invents is born gitignored. What is
left for you is **every `out:` path in `outputs:` that you wrote by hand**. Generated
outputs must be gitignored without exception: `wet setup` generates them in the
main checkout at slot 0 too, so a *tracked* `out:` is rewritten and left dirty
on every run — and if it carries secrets, one `git commit -a` puts them in the
history.

## Common patterns

### Docker Compose with per-worktree ports

**IMPORTANT: env file layering.** Docker Compose uses `--env-file` for
compose-level variable interpolation (`${APP_PORT:-8080}` in the YAML).
`.env.worktree` has port overrides but NOT database credentials or secrets.
Those typically live in a separate `.env` file (e.g. `web/.env`, `backend/.env`,
or `.env` at the repo root). You MUST pass BOTH files so compose has access
to everything:

```yaml
hooks:
  post_create:
    # --env-file order matters: first file provides base vars (DB creds etc.),
    # second file overrides ports. Later values win on duplicate keys.
    - "docker compose -f web/docker-compose.yml --env-file web/.env --env-file .env.worktree -p {{.ProjectName}}-{{.BranchSafe}} up -d"
  pre_remove:
    - "docker compose -p {{.ProjectName}}-{{.BranchSafe}} down"
```

**When helping the user write this hook**, always ask: **"Where does your
docker-compose.yml live, and where are your DB credentials / secrets stored?"**
Common patterns:
- `web/.env` or `backend/.env` — credentials in a subdirectory alongside the compose file
- `.env` at the repo root — credentials at the top level
- `docker-compose.yml` uses `env_file:` inside the YAML for container env — this is SEPARATE from `--env-file` on the CLI. The container-level `env_file:` paths are relative to the compose file's directory and load independently.

If the project has NO separate credentials file (everything is in env vars or
hardcoded), a single `--env-file .env.worktree` suffices. But always check —
missing DB passwords is the #1 failure mode for worktree Docker boot.

In the docker-compose.yml itself, parameterize host ports with defaults:
```yaml
services:
  app:
    ports:
      - "${APP_PORT:-8080}:8080"
  db:
    ports:
      - "${DB_PORT:-5432}:5432"
```

### Point editor config at the generated env file

The first move for `launch.json` and friends is **not** to generate them. Ask
whether the tool can read an env file — most can — and if so, keep the editor
config plain and committed:

```jsonc
// .vscode/launch.json — identical in every worktree, so just commit it
{"configurations": [{
  "name": "app (dev)", "request": "launch", "type": "dart",
  "args": ["--dart-define-from-file", ".env"]   // VS Code node/python: "envFile"
}]}
```

`.env` is a declared `outputs:` entry, so it already carries this worktree's
ports. launch.json then holds nothing that varies, and needs no generation, no
gitignore juggling, and no `--assume-unchanged`.

Tell the user to leave host, port, and device **out** of the JSON. A pinned
port is right in exactly one worktree; a committed device id points at
hardware their colleagues don't have. Device selection belongs in the editor's
device picker or a `just` recipe that reads the worktree's allocation.

### When the tool can't read an env file at all

**wet cannot generate it.** `format: dotenv` is the only encoder — there is no
text-template engine any more, so wet cannot produce a JSON, TOML, or XML config
file. Do not promise the user one, and do not suggest a `render:` block: that
key is removed and a config containing it fails to load.

Say so plainly and offer the two honest options:

1. **A `just` recipe (or any script) in their repo** that reads the generated
   dotenv or `.env.worktree` and writes the file. It is their project's
   knowledge, in their project, and a `post_create` hook can call it.
2. **The sed last resort below**, if the file is huge, hand-maintained, and only
   one line varies.

If the request is "make wet write `<framework file>`", the answer is a hook
calling their script, never a new wet feature. wet contains no project
knowledge.

### Patching a tracked file with sed (last resort)

Only when the file cannot be generated from a template — e.g. it is huge,
hand-maintained, and only one line varies. Patching a tracked file makes it
show as modified, and users will commit per-worktree ports back to the shared
branch, so it needs `git update-index --assume-unchanged` as the last step:

```yaml
hooks:
  post_create:
    - sed -i.bak 's/"port": 40000/"port": {{.DEBUG_PORT}}/' .vscode/launch.json
    - rm -f .vscode/launch.json.bak
    - git update-index --assume-unchanged .vscode/launch.json
```

Be honest with the user about the cost: `--assume-unchanged` is permanent and
indiscriminate. It hides *every* later change to that file, including edits
they make deliberately and expect to commit. `.gitignore` and
`.git/info/exclude` are no help — both only apply to untracked files. Undo with
`git update-index --no-assume-unchanged <file>`.

**If you find yourself writing a sed hook, first ask whether the tool could read
a generated env file instead.** Usually it can, and then none of this applies.

### Create a PR from a worktree
`wet pr create` pushes the branch and opens a GitHub PR. Title auto-generated from branch name. Flags: `--draft`, `--fill`, `-t "title"`, `-b base`.

## Generated env files (`outputs:`)

Every environment file wet generates is declared inline under `outputs:`. There
is no checked-in `.env.tpl` and no `render:` block: for a dotenv file wet
already knows every value, so the only thing left to declare is which values the
file carries and under what key. That makes `.wet.yaml` the whole inventory —
one file answers what is generated, what each file holds, and which of those
keys are secrets.

Prefer this over listing a generated `.env` in `copy:`. A copy snapshots one
machine's values and then drifts; a declared output always carries this
worktree's own ports.

```yaml
outputs:
  - name: backend                 # CLI identifier: `wet env pull backend`
    out: backend/.env.dev         # relative to the checkout being configured
    format: dotenv                # the only format
    include:                      # keep the wet name as the output key
      - AUTH_BASE_URL
      - DATABASE_URL
      - PHX_PORT
    secrets:                      # only these definitions are visible here
      - SECRET_KEY_BASE
      - GOOGLE_CLIENT_SECRET

  - name: mobile
    out: mobile/.env
    format: dotenv
    mode: "0644"                  # optional octal string; default "0600"
    values:                       # rename, or write a fixed value
      host:         { from: DEV_HOST }
      port:         { from: GRPC_PORT }
      webBaseUrl:   { from: AUTH_BASE_URL }
      device:       { from: Handles.devices }
      oidcClientId: { literal: myapp-mobile }
```

Field by field:

- `name` — required, unique, `[a-z0-9][a-z0-9_-]*`. It is what
  `wet env pull <name>` and `wet env push <name>` select.
- `out` — required, relative, must not escape the checkout, and no two outputs
  may write the same path. Missing parent directories are created.
- `format` — required. `dotenv` is the only supported value.
- `mode` — optional octal string (`"0644"`). Default `0600`, because a
  generated env file may carry secrets and outlives the command that wrote it.
- `include` — ordinary values, declared ports, or reserved fields, keeping their
  own names as output keys.
- `secrets` — names from `secrets.definitions:`, also keeping their own names.
- `values` — output key → `{ from: <name> }` or `{ literal: <scalar> }`.
  Exactly one of the two; both or neither is an error. `from:` accepts an
  ordinary value, a port, a reserved field, or a `Pools.<name>` /
  `Handles.<name>` pick.

An output must declare at least one key across the three.

Keys are emitted in declaration order: `include`, then `secrets`, then `values`
in the order they were written. This is a guarantee, not an accident — write
`values:` in the order the generated file should read. Every generated file opens with
`# Generated by wet. Do not edit — change outputs: in .wet.yaml.`

### Rules to state to the user before writing an `outputs:` block

- **A secret is never renamed.** `include:` refuses a secret name and points at
  `secrets:`; `values.<key>.from:` refuses one outright. Secrets are emitted
  only through `secrets:`, under their logical name. A rename must not be able
  to smuggle a credential into a file that did not select it.
- **`include:` may only name something `.wet.yaml` declares** — a reserved
  field, a `ports:` entry, or an `env:` key. Not a `.env.local` key:
  `.env.local` *overrides* declared values, it never introduces new ones, so a
  key that exists on one workstation cannot become an output's contract.
- **The same output key may not be claimed twice**, including across `include`,
  `secrets` and `values`.
- **The `out:` path must be gitignored.** `wet setup` also generates in the main
  checkout at slot 0, so a tracked output is rewritten and left dirty every run.
- **No newlines in values.** A value containing one is rejected rather than
  escaped — dotenv dialects disagree about multi-line values, and a value that
  half-parses puts the tail of a private key on a line the reader treats as the
  next assignment. Tell the user to base64-encode PEM material into a
  single-line secret.
- **Generated files are wet's to own.** Re-running `wet env pull` is how a
  checkout is repaired, so it needs no flag and a hand-edit does not survive it.
  Per-machine values go in `.env.local` or `.wet.local.yaml`.

Everything above that is checkable from `.wet.yaml` alone is checked at load, in
every command, before a store is contacted or a byte is written.

### Commands

```bash
wet env pull                     # regenerate every declared output
wet env pull backend             # just that one
wet env pull --dry-run           # resolve and validate, write nothing
wet env pull --secrets=disabled  # override secrets.policy for this run
wet env explain                  # what each output holds and where its secrets live
wet env explain backend
```

`wet setup` runs the same pull itself, after `.env.worktree` is written and
**before** `post_create` hooks — so a hook that boots the stack finds its env
files already present, and no hook needs to generate them. A config that
declares no `outputs:` skips the step: there is nothing to generate.

`wet env pull` does *only* that. It does not register a worktree, allocate or
change a slot, ports or pool items, write `.env.worktree`, or run hooks. So it
is always safe to re-run. Every requested output is resolved and validated
before any is written, so a failure in the second cannot leave the first already
replaced.

`--dry-run` still contacts the secret store, because whether a `required` secret
exists is exactly what a dry run is asked to find out. It never prints a value.

`wet env explain` reads `.wet.yaml` only — no worktree, no store, no values.

Inside a `post_create` hook, a pull reads `$SLOT` / `$BRANCH` / `$APP_PORT` from
the hook environment, because hooks run *before* `.wet-worktrees.json` is
written. Run by hand afterwards it reads the state file. Same values either way.

## Secrets

Optional. Without a `secrets:` block wet contacts no store at all, and outputs
carry ordinary values only.

```yaml
secrets:
  store: op                 # only 1Password is implemented
  policy: fallback          # required | fallback | disabled — default fallback
  item: backend-development # the item the fields sit on — a project fact
  vault: Development        # the vault holding it — also a project fact
  # account: is NOT here — it is machine-local, and belongs in the gitignored
  # .wet.local.yaml under this same secrets: key.
  definitions:
    SECRET_KEY_BASE:
      field: secret_key_base
      default: dev-only-secret-key-base
    SENTRY_DSN:
      field: sentry_dsn
      default: ""                     # deliberately unconfigured locally
    STRIPE_KEY:
      field: api_key
      item: stripe                    # per-secret override of the block's item
    LEGACY_TOKEN:
      ref: op://Shared/legacy/token   # or a full reference instead
```

A definition is `field:` plus optional `vault:` / `item:` overrides, **or** a
full `ref:` — never both, because a half-overridden reference is ambiguous.

Rules worth stating to a user before writing this block:

- **Definitions name credentials, never consumers.** `GOOGLE_CLIENT_ID` is one
  credential whether the API or the app reads it, so the vault holds no
  per-consumer duplicates and a rotation is one edit. Never suggest
  `backend_google_client_id` style field names — an output's `secrets:` list
  already carries that meaning, in the config where it belongs.
- **Scope is per output.** Defining a credential does not hand it to every
  generated file; an output sees exactly the definitions it lists. A mobile or
  other client-facing output should list none — everything in a shipped client
  must be assumed public.
- **No paths in the secrets block.** Where a value lands is the `out:` of the
  output that selected it.
- **`default: ""` is a real value**, distinct from omitting `default:`. The
  empty string says "this provider is deliberately not configured locally";
  omitting it says "there is no safe stand-in, fail loudly".
- **A secret name must look like an env var** (`[A-Z_][A-Z0-9_]*`), must not be
  a reserved field, and must not collide with a declared port or an `env:` key.
  If the user has a development fallback sitting in `env:` under the same name,
  move it into the definition's `default:` — that collision is a hard error.
- **`vault` and `item` belong in `.wet.yaml`; only `account` is machine-local.**
  Where the project's credentials live is the same answer for everyone who
  clones the repo. Do not put an account in `.wet.yaml` unless the whole team
  signs into the same one. `.wet.local.yaml` can override the vault like any
  other key — but that is an override, not where it belongs.
- **`.env.local` cannot override a secret.** Secret values reach a generated
  file only from the store or from a declared `default:`.

### Don't hand-write the keys — scaffold them

`wet secrets setup` writes a provider's keys into `.wet.yaml` across all three
blocks, wired together. **Reach for it before writing any credential block by
hand.**

```bash
wet secrets setup                 # multi-select of the catalog
wet secrets setup google apple    # or name the groups
wet secrets setup google --output web
wet secrets groups                # what each group contains
wet secrets setup --dry-run       # print the result instead of writing
```

What it does with each catalog key:

- A **credential** becomes `secrets.definitions.<KEY>: {field: …, default: …}`,
  carrying the catalog's development fallback in `default:`. If the file has no
  `secrets:` block it creates one with `store: op` and `policy: fallback`.
- A **derived or plainly public value** — a redirect URI built from this
  worktree's ports — stays an ordinary `env:` entry. Storing one would pin every
  checkout to the same URL.

Both lists are then wired into an `outputs:` entry — `backend` unless
`--output` names another — appending to its `include:` and `secrets:`, and
creating the output (`out: <name>/.env.dev`, `format: dotenv`) if none exists by
that name. That last step is the point: a definition no output selects is
inert, and `wet env pull` would write exactly what it wrote before, which reads
as wet ignoring the provider the user just added. Tell the user when an output
was invented and check `out:` is where their app actually reads.

Nothing existing is touched: a filled-in value survives a re-run, a name an
output already selects is not re-listed, and a credential already sitting in
`env:` is left as an ordinary value rather than moved. The result is validated
through the real loader before it is saved.

`wet setup` offers the same picker when it scaffolds a starter config.

The catalog is built into the wet binary — what `google` means is a fact about
Google, not about the user's project — so a group gains keys on a wet upgrade,
not when someone remembers to copy a file.

### Secret policy

`secrets.policy:` says what happens when the store cannot answer;
`wet env pull --secrets=<policy>` overrides it for one run.

| Policy | Behavior |
|---|---|
| `required` | Every selected secret must come from the store. A declared `default:` deliberately does **not** substitute — this mode exists so a project can be certain the real credential is what landed in the file. |
| `fallback` (default) | Try the store; on any failure — `op` missing, not signed in, item absent, field absent — use the declared `default:`. A secret with neither store value nor default is an error. |
| `disabled` | Never contact the store. Declared defaults must satisfy every selected secret. For offline work and deterministic tests. |

`fallback` is the default because it is the only policy under which a fresh
clone with no store access still boots — and it is never silent. Each output
gets a provenance line, names only, never values:

```text
  Secrets for backend/.env.dev: 7 from 1Password, 3 defaults
    defaults: ADMIN_EMAILS, POSTMARK_API_KEY, SENTRY_DSN
```

Each distinct reference is fetched once per run across all outputs — one round
trip, and one authorization prompt.

### Where the account and vault come from

No command sets them. The credential map is committed in `.wet.yaml`; which
account you are signed into and which vault you use are facts about your
workstation, so they are the two keys the gitignored overlay carries:

```yaml
# .wet.local.yaml
secrets:
  account: my.1password.com
  vault: Development
```

Until the vault is set, `policy: fallback` writes each secret's declared
`default:` and names which ones fell back; `wet env explain` reports the
missing destination instead of failing.

### `wet env push` — declared secrets, back into the store

```bash
wet env push backend --from backend/.env.dev --dry-run
wet env push backend --from backend/.env.dev
```

**The named output is the authorization boundary.** wet writes a key only when
it is both declared under `secrets.definitions:` and listed in that output's
`secrets:`. Everything else in the file — ordinary configuration, unknown names,
a secret belonging to another output — is ignored and reported. There is no flag
that lets an undeclared key reach the store, and a destination mapping cannot be
invented on the command line. A mixed generated file is therefore a normal
input and needs no permissive flag.

**A value equal to that secret's declared `default:` is refused by default**,
reported as `fallback value — not pushed`. A file generated under `fallback` is
full of development placeholders, and pushing an empty string or a dev-only key
over a real credential is the one mistake this command must never make.

| Flag | Effect |
|---|---|
| `--from <file>` | dotenv file to read (required) |
| `--dry-run` | print every destination and status, write nothing |
| `--force` | overwrite a field holding a different non-empty value (otherwise reported as a conflict and left alone, so re-pushing a stale file cannot undo a rotation) |
| `--create-item` | create the destination item; a missing item is otherwise an error |
| `--reject-unmapped` | fail if the source holds any key this output does not select — for a dedicated secrets-only import where a typo should be loud. It does not widen what wet may write. |
| `--include-defaults` | also push values equal to a declared `default:` |

Names, destinations and statuses are printed. Values never are.

## Migrating a config off `render:`

If a user's `.wet.yaml` still has `render:` or `secrets.sections:`, it will not
load — wet fails with a message naming the replacement. Migrate it:

1. One `outputs:` entry per `render:` target: the target's `out:` becomes `out:`,
   plus `name:` and `format: dotenv`.
2. Read the target's `.env.tpl` and turn each line into a key. `KEY={{.KEY}}`
   becomes `include: [KEY]`; `alias={{.SOURCE}}` becomes
   `values: { alias: { from: SOURCE } }`; a constant becomes
   `values: { alias: { literal: … } }`. Anything doing real template logic has
   to be resolved by hand — usually by adding an `env:` entry that computes it,
   which is where it belonged anyway.
3. Each `secrets.sections.<section>.<KEY>: <field>` becomes
   `secrets.definitions.<KEY>: { field: <field> }`, defined once even if several
   sections named it. List the names each output needs under that output's
   `secrets:`.
4. Move development fallbacks out of `env:` into the matching definition's
   `default:` — a secret and an `env:` entry may no longer share a name.
5. Delete the `.env.tpl` files and the `render:` / `sections:` blocks.

Then run `wet env explain` and `wet env pull --dry-run` and compare against the
files the old setup produced, before deleting anything irreversible.

## `wet setup` — one bootstrap for main and worktrees

`wet setup` configures whichever checkout it is run in. A worktree gets slot
N; the main repo gets slot 0 — the declared `base:` ports, its own pool claim,
its own generated env files — skipping only `copy:` (no source to copy from).
This is why a fresh clone and a fresh worktree bootstrap with the same command,
and why a main checkout whose emulator was deleted re-claims one by re-running
setup instead of being hand-fixed.

Destructive lifecycle stays worktree-only: `pre_remove` and `wet worktree pop`
never run against main. When writing a `.wet.yaml`, assume every `post_create`
hook will also run in the main checkout, and keep anything irreversible out of
it.

## Monorepos — derive once, emit many

Several packages, several env files, all descending from the same ports. Do
NOT give each output its own copy of the derivation — they drift. Derive in
`env:` (entries may reference each other, resolved to a fixed point, so order
doesn't matter), then declare one `outputs:` entry per package:

```yaml
env:
  DEV_HOST:      "localhost"
  AUTH_BASE_URL: "http://{{.DEV_HOST}}:{{.PHX_PORT}}"
  CALLBACK_URL:  "{{.AUTH_BASE_URL}}/callback"

outputs:
  - name: web
    out: web/.env.dev
    format: dotenv
    include: [AUTH_BASE_URL, CALLBACK_URL, PHX_PORT]
    secrets: [SECRET_KEY_BASE]

  - name: mobile
    out: mobile/.env
    format: dotenv
    values:
      host:       { from: DEV_HOST }
      webBaseUrl: { from: AUTH_BASE_URL }
      port:       { from: GRPC_PORT }
```

- `wet setup` generates every output before hooks run; `wet env pull` (add
  `--dry-run`) does it on demand, and `wet env explain` lists what each holds.
- Each output is resolved against its own scoped view — one output's secrets
  cannot reach another's file, and the mobile output above can see none at all.
- Renaming belongs in the output (`port: { from: GRPC_PORT }`), not in `env:`.
  Adding a per-consumer alias to `env:` is how the derivation layer starts
  growing one entry per reader.
- Two outputs writing the same `out:` is rejected at load time.
- A gitignored `.env.local` beside the trunk checkout (`KEY=value`) overrides `env:`
  entries per machine, and the override propagates into everything derived
  from it. Put a LAN IP for physical-device testing there, never in
  `.wet.yaml`. It cannot introduce a new key, and it cannot override a secret.

When probing a project, look for the same fact being rebuilt in several
places — a compose `environment:` block, a Justfile shell snippet, a
hand-maintained `.env` — and collapse them into one `env:` entry.

## `.wet.local.yaml` — machine-local overrides

A gitignored overlay beside `.wet.yaml`. Optional file, optional keys: it names
only what it changes, everything else falls through.

Put anything machine-specific there — device IDs above all, since a committed
`pools:` list is what makes a `.wet.yaml` unshareable:

```yaml
pools:
  devices: [RFCR921L4DP, "emulator:wet-myapp-1"]
pool_grow:
  devices: android-emulator
```

- Any top-level key is overridable (`port_stride`, `ports`, `hooks`, …) — the
  merge happens in the loader, so nothing downstream knows the file exists.
- Maps merge key by key; **sequences replace wholesale** (a local pool is your
  list, not yours appended to someone else's).
- The merged result is validated as a whole; errors name the local file.
- `pool_grow` records new AVDs here, never in the committed config.

**When writing a `.wet.yaml`, keep `pools:` out of it** unless every item is
portable, and tell the user to put their device IDs in `.wet.local.yaml`.
Emulator items are always `emulator:<AVD_NAME>`, never an `emulator-NNNN`
serial — the serial is transient and unbootable once the emulator stops.

Also: `pool_grow: android-emulator` grows AVDs, so it belongs with the
machine-local pool, and a pool mixing physical devices with emulators is fine
— growth ignores non-emulator items.

## Validation rules

- `project_name`: `[a-z0-9][a-z0-9_-]*`
- Port `name`: `[A-Z_][A-Z0-9_]*`, must not collide with reserved fields (`ProjectName`, `Branch`, `BranchSafe`, `Slot`, `Pools`, `Handles`)
- Pool `name`: `[a-z_][a-z0-9_]*`, same reserved-name check
- Copy paths: no `..`, no leading `/`
- `env:` and hook strings: parsed as Go templates at load time (syntax errors fail early)
- Slot 0 reserved for main; worktrees start at 1
- Output `name`: `[a-z0-9][a-z0-9_-]*`, unique across `outputs:`
- Output `out`: relative, no `..`, unique across `outputs:`
- Output `format`: must be `dotenv`; `mode`: an octal string like `"0600"`
- Every output declares at least one key across `include` / `secrets` / `values`
- `include:` names a reserved field, a declared port, or an `env:` key — never a secret
- `values.<key>`: exactly one of `from:` / `literal:`; `from:` never names a secret
- No output key claimed twice across `include`, `secrets` and `values`
- `secrets.store`: must be `op`; `secrets.policy`: `required` | `fallback` | `disabled`
- `secrets:` requires at least one entry under `definitions:`
- Secret `name`: `[A-Z_][A-Z0-9_]*`, not a reserved field, and must not collide with a declared port or an `env:` key
- A definition needs `field:` **or** `ref:` (a full `op://vault/item/field`), never both; `field:` must be a bare name with no `/`
- An output's `secrets:` may only name a defined secret
- `render:` and `secrets.sections:` present: hard load error with a migration message

## Hook environment quick-ref

Hooks get every value twice: as a template field expanded before `sh -c` runs,
and as a real environment variable the command (or a script it calls) can read.

| Template | Shell env var | Example |
|---|---|---|
| `{{.ProjectName}}` | `$PROJECT_NAME` | `myapp` |
| `{{.Branch}}` | `$BRANCH` | `feature/foo` |
| `{{.BranchSafe}}` | `$BRANCH_SAFE` | `feature-foo` |
| `{{.Slot}}` | `$SLOT` | `1` |
| `{{.APP_PORT}}` | `$APP_PORT` | `8090` |
| `{{.Pools.devices}}` | `$POOL_DEVICES` | `emulator:wet-myapp-1` |
| `{{.Handles.devices}}` | `$POOL_HANDLE_DEVICES` | `emulator-5554` |
| every `env:` key | `$<KEY>` | `$COMPOSE_PROJECT_NAME` |

Pool names uppercase into the var name: pool `test_fixtures` becomes
`$POOL_TEST_FIXTURES` / `$POOL_HANDLE_TEST_FIXTURES`.

## Debugging

- **Hook failure on create**: recovery block printed with worktree path, failing hook, and exact command. Worktree left on disk, not recorded in state. Fix cause → `git worktree remove --force` → `git branch -D` → retry.
- **Hook failure on pop**: worktree NOT removed. Fix and retry.
- **Port collision**: bump the `base:` or use per-port `stride:` override.
- **"uses the removed `render:` key"** (or `secrets.sections:`): the config is on
  the old schema. Migrate it — see "Migrating a config off `render:`". There is
  no compatibility flag, on purpose: a config that still parsed would generate
  nothing and leave a stale `.env.dev` on disk looking current.
- **A key is missing from a generated file**: run `wet env explain <output>`.
  Either the output never declared it, or it is a secret the output did not
  select — scope is per output, so defining a credential is not enough.
- **A secret came out empty**: the provenance line after each pull names every
  key that fell back to its declared `default:`. Sign in to the store, or run
  `wet env pull --secrets=required` to make a store failure fatal instead.

# Team guide

Use this when the user wants to boot the dev stack and spawn an agent team. Works from the main repo or from an wet worktree.

## Step 0 — Detect context

```bash
REPO_ROOT=$(git rev-parse --show-toplevel 2>/dev/null)
if [ -f "$REPO_ROOT/.env.worktree" ]; then
  echo "=== WORKTREE MODE ==="
  echo "WORKTREE_ROOT=$REPO_ROOT"
  cat "$REPO_ROOT/.env.worktree"
else
  echo "=== MAIN MODE ==="
fi
# What agents are available?
ls "$REPO_ROOT"/*/.claude/agents/*.md "$REPO_ROOT"/.claude/agents/*.md 2>/dev/null || true
```

**Worktree mode** (`.env.worktree` exists): source it for `APP_PORT`, `DB_PORT`, `COMPOSE_PROJECT_NAME`, `FLUTTER_DEVICE_ID`, etc. **CRITICAL: all commands and all spawned teammates must use `$REPO_ROOT` (the worktree root), never the main repo path.** The worktree is a full copy — `mobile/`, `web/`, etc. all exist inside it.

**Main mode**: use defaults from `.wet.yaml` port bases, or fall back to common defaults (8080, 5432).

## Step 1 — Discover what this project has

Not every project has a backend, a mobile app, or Docker. Detect what exists before doing anything:

```bash
# Backend: look for docker-compose or a Go/Node/Python server
ls "$REPO_ROOT"/**/docker-compose.yml "$REPO_ROOT"/docker-compose.yml 2>/dev/null || true
# Mobile: look for a Flutter project
ls "$REPO_ROOT"/**/pubspec.yaml 2>/dev/null || true
# Running services
docker compose ps --format json 2>/dev/null || true
pgrep -fl 'flutter run' 2>&1 || true
which flutter >/dev/null 2>&1 && flutter devices --machine 2>/dev/null || true
```

Only include components that actually exist in the pre-flight report:

```
Team pre-flight (<worktree: branch slot N  OR  main>)
  backend     ✓ up (:$APP_PORT)   or   ✗ down          or   — (no backend found)
  mobile      ✓ running           or   ✗ not running   or   — (no Flutter project)
  devices     <list>              or   n/a
```

## Step 2 — Boot what's missing

Only boot components that exist in this project. Skip sections that don't apply.

**Backend** — only if a docker-compose.yml exists:
- Worktree: find the compose file AND the credentials env file (e.g. `web/.env`, `backend/.env`, or `.env`). Pass both: `docker compose -f <compose-file> --env-file <creds-env> --env-file .env.worktree -p $COMPOSE_PROJECT_NAME up -d`. The creds file provides DB passwords etc., `.env.worktree` overrides the ports. **Missing this is the #1 failure mode** — always check for a separate `.env` file near the compose file.
- Main: `cd <compose-dir> && docker compose up -d` (auto-loads the local `.env`).
- Poll port ~15s. Never `down -v`, `prune`, `rmi`, or `--build` unless asked.

**Mobile** — only if a `pubspec.yaml` exists. **Always launch the app** — don't wait to be asked:
- Use the device assigned to this worktree (`$FLUTTER_DEVICE_ID` from `.env.worktree`, or the pool-allocated device ID). Never prompt for device selection — the pool handles it.
- Android: `wet mobile reverse-tcp` first — it reverses every port this worktree was allocated onto the device it claimed. Never hand-roll `adb reverse`: without `-s` it dies with "more than one device/emulator" the moment a second worktree has a device up.
- Launch with `flutter run -d $FLUTTER_DEVICE_ID` in background (`run_in_background: true`).
- Confirm the app is running on the device before proceeding to Step 3.

## Step 3 — Discover and spawn teammates

Scan for agent definitions:
```bash
ls "$REPO_ROOT"/*/.claude/agents/*.md "$REPO_ROOT"/.claude/agents/*.md 2>/dev/null
```

Spawn one teammate per agent definition found. **Include the worktree root path (`$REPO_ROOT`) in each spawn prompt** so teammates work in the worktree, not the main repo. Include worktree context (ports, device, status) in each spawn prompt. Each teammate reads its own CLAUDE.md, confirms in one sentence, then stands by.

**Rules:**
- Don't invent teammates beyond what agent definitions exist.
- Don't inline agent definitions.
- One team per session.
- **Do not auto-start work.** Wait for the user.

## Step 4 — Report

Only include lines for components that exist. A mobile-only project should NOT show a backend line:

```
Team — ready
  context     <worktree: branch slot N  OR  main repo>
  ✓ backend   <status>   :$APP_PORT              ← only if backend exists
  ✓ mobile    <status>   device: $DEVICE_ID       ← only if Flutter project exists
  ✓ team      N teammates: <names>
  > next      Tell the lead what to work on
```

## Guardrails

- **Never** destroy state (no `-v`, no `prune`, no `--build`).
- **Never** silently pick a device when multiple are connected (unless worktree pre-assigned one).
- **Never** start Flutter in the foreground.
- **Never** loop on boot failures — show logs and stop.
- **Never** duplicate agent definitions inline.
- **Never** run commands or edit files in the main repo when in worktree mode. All paths must be relative to `$REPO_ROOT` (the worktree root).
